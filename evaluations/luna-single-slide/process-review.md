# 制作過程の独立レビュー

対象要件は「要約、図版選定、レイアウト実装、文言調整、全体デザイン調整の全般的プロセスを評価」「監督者はscope/概略役割/情報源のみ」です。画像の匿名判定をすべて保存した後に制作記録を読み、以下の過程評価を行いました。出自開示後も画像判定は変更していません。

## 指摘事項

### 1. 重要：今回の完了を、検査を含む無介入の本番自律運用の成功とは扱えません

Case 1の正式チェッカーは `status: fail` です。`visual_manifest.tsv` 未指定とPyMuPDF未導入によってPDFを観測できていません。復旧ログ60行目と保存済み `case-1/outputs/audit/deck-check.json` が一致します。複合コマンドの終了コード0は、末尾の `cat` が成功した結果であり、チェッカー合格の根拠にはなりません。制作者の最終通知は失敗を開示しているため、合格を偽装したとは評価しません。ただし「品質の失敗ではなく観測不能」であることは、検査完了を意味しません。

Case 2は依存不足を自分で補修して再試行し、最終的にははみ出し検査に合格しています。復旧ログ27行目のnumpy不足、39行目の導入、41・47・56行目の成功を確認しました。45行目では別の検査が `No module named 'pptx'` で失敗しているのに、後続コマンドにより全体が終了コード0となっています。この失敗も47行目で回復していますが、Case 1だけでなく複合コマンド全般で失敗を判定から落とす危険があることを示します。

今回の3ページの画像採用を取り消す問題ではありません。一方、正式検査を終えないまま機械的に本番納品を承認する運用は承認しません。改善は、検査ごとの結果を確認し、必要な検査が `pass` か「未実施・適用外・代替確認済み」のどれかを明記してから納品状態を決めることです。全チェッカーや全描画環境への対応を一律に要求する必要はありません。

### 2. 重要：文言推敲と目視確認の過程は、結果の存在に比べて証拠が弱い状態です

Case 1・3の生成ソース更新は直接確認できますが、JSONLの `file_change` はパスと追加・更新の種別だけで本文差分を含みません。Case 1の留保追加や「RF → Radiance Field」の修正は `process_record.md:30` 以降の自己申告であり、変更前後と変更順序をこの記録から再現できません。Case 3も同様です。したがって「文言が最終的に適切か」は画像レビューで評価できますが、「どの推敲で改善したか」「反復的に日本語を調整する能力が確認できたか」は限定的な判定になります。

再描画のコマンドと生成ファイルは直接記録されています。一方、3件の元ログ・復旧ログには `view_image` を含むイベントがなく、実際に何を見てどの問題を検討したかは制作記録・完了通知による自己申告です。これは「目視をしなかった」という証明ではなく、CLIログから独立に確認できないという限界です。匿名画像レビューは完成表示を別に確認しましたが、制作中の確認実施を遡って証明するものではありません。

改善は、最初の完成版と最終版、意味を変えた主要な修正の「変更前 → 変更後 → 理由」を数行残すことです。目視については確認した画像・ページと具体的な結果を残します。全キー操作の記録、新たな大規模台帳、毎回の外部Reviewerは必要ありません。

### 3. 中程度：図候補調査がFigure 1中心で、Case 1では中心機構の説明力を落としています

Case 1の復旧ログ13・16行目は各論文のFigure 1を探索し、20・26行目はそのページの描画・切り抜きを示します。14行目の進捗も「各論文の図1」を採用する構成です。別番号の方法図との採否比較は確認できません。匿名画像判定でも、生成例は出力や用途を伝える一方、Shap-Eの関数パラメータ生成やTRELLISの二段階生成を直接説明しないことを指摘しました。したがって、Case 1ではログ上の候補の狭さと完成画像の説明上の不足が対応しています。

ただし「Figure 1だから不適切」と一般化するのは過剰です。Case 2の役割は表現形式の関係・移行であり、Occupancy Networks Fig. 1がその問いに直接答えます。Case 3も共通原理を図、モデルの違いを式と文で説明する設計として成立しています。3論文それぞれから図を1点ずつ追加することは要求しません。

改善は、中心主張が「生成例」か「機構」かを先に確認し、候補図がそれを見せない場合に方法図を1点比較することです。Case 1ではTRELLIS Fig. 2などを比較候補にすると具体的な改善につながります。図数や候補数の固定ノルマは不要です。

### 4. 中程度：Case 3の環境記述に、存在確認をせず断定した誤記があります

`case-3/outputs/production_log.md:24` の「参照先Markdown自体は復元されていない」は、復旧記録と一致しません。元ログ16行目の参照ファイルへの `cat` は成功しています。復旧ログ9行目の `rg --files` は `references/*.md` を対象に含めない限定的なglobで、そこに表示されないことから未復元とは判断できません。復旧ログ11行目は `SKILL.md` の読み込み成功ですが、参照先への `cat` や `ls` が失敗したものではありません。

本レビューでも `runs.json` の各workdirを対象に、`recovery-observations.json` の52ファイルを読み取りハッシュで照合しました。全3ケースに欠落0・差分0で、参照ファイルも現在存在しています。この再照合は現在の状態の確認であり、制作時点の完全な証明ではありませんが、時点付きの復旧時・完了後の照合記録とも整合します。

親の訂正は妥当です。推測の理由までは確定しません。原記録を保存し、復旧報告と訂正記録を併記している現状を承認します。改善は、環境の不存在を断言する前に対象ファイルへの存在確認を一度行い、できなければ「未確認」とすることです。

## 依頼設定と復旧の妥当性

3プロンプトは共通の制作・納品・検証指示と禁止範囲に加え、scope/roleとbibliographyを与えています。図、中心主張、要約、配置の答えは記載されていません。今回の要件にいう「監督者はscope/概略役割/情報源のみ」は、内容に関する助言の範囲として守られています。制作・納品の共通指示や固定版スキルの提供はありますので、「情報源以外の指示が一切ない」と解釈するのは正確ではありません。

元のプロンプト3件のSHA-256は `runs.json` と一致しました。元イベントと復旧イベントの `thread.started` も3件それぞれ同一IDです。再開文は一時ディレクトリ消失、固定版復元、既存履歴からの再生成、ネットワーク補修を伝えています。提示された再開文に内容助言はありません。元ログにはCase 1のDNS関連エラー（57行目）とCase 2の名前解決失敗（33行目）、復旧ログにはCase 1自身のHTTP 200（11行目）があり、ネットワーク補修の説明は直接記録と整合します。

モデル `gpt-6-luna`、effort `high`、同一thread、固定版52ファイルを保持した復旧として評価できます。ハッシュ照合、内容助言を含まない再開文、制作者による原典取得・再生成は復旧方法を支持します。検査した範囲に監督者が文面や配置を手修正した記録はありません。

ただし監督者による環境修復を受けた再開実行なので、無介入の新規実行、クラッシュ前だけの成績、最新版スキルの成績とは区別する必要があります。クラッシュの原因をLunaやスキルへ帰属する証拠もありません。「内容への介入がない」と「環境介入がない」は別の評価です。

## 監督側診断との照合

- **妥当**：原典取得・切り抜き・生成・構造検査と、読解・目視の自己申告を区別した整理は記録に沿っています。Case 1の正式checker fail、Case 2のフォント変更、Case 3の復元記録誤記はそれぞれ原イベントや保存物で確認しました。
- **限定すべき点**：Figure 1偏重は選択過程の狭さを示しますが、全ケースの図選定失敗を意味しません。文字差分の不足は推敲未実施の証明ではなく、推敲過程を評価する証拠の不足です。`view_image` の欠如も目視未実施と同一ではありません。
- **追加の重要点**：失敗する複合コマンドでも後段成功で終了コード0になる例はCase 2にもあります。検査の各結果を読む必要があります。またCase 1の「G4-P go」は、最初のPDF生成（復旧ログ40行目）後に追加された記録（46・47行目）にあります。本人が制作前に自己確認した可能性は残りますが、時点付きの制作前レビューを直接記録したものではありません。
- **追加の運用上の限界**：Case 1/2のPDFは画像形式、Case 3は文字抽出可能で、編集用正本もSVGとPPTXに分かれます。要求された編集可能ソースとPDFの提供自体は満たしますが、講義全体への統合や再生成の環境管理は別途必要です。単ページ評価で形式を一律に統一する要求は出しません。

## 採用・本番運用・終了判断

今回の3単ページは、匿名画像比較でそれぞれ採用を承認した判定を保持します。開示された対応では3件とも今回のLuna生成物が採用対象となりました。ただし、Case 1では図の機構説明と比較項目の揃え方、Case 2では見出しの範囲、Case 3では小さな文字や図の注釈に改善点があります。3件の採用は、各ページの役割と完成画像を評価した結果です。

**mainへのマージ**：限定された評価記録と成果物を、正式checker fail・復旧条件・未確認範囲・Case 3訂正を保持して取り込むことは承認します。この範囲のマージを阻害する残件は認めません。元記録の誤記を隠す、チェッカー合格や最新スキルの改善を根拠なく宣言する形での取り込みは承認しません。リポジトリ全体のコード安全性を評価したものではありません。

**本番運用**：独立レビューを経た今回の3ページの利用と、記録付きの監督下の制作試行は承認します。環境修復や検査未完了を含む今回の実績を根拠として、無介入の大量生成・自動納品が安定しているとする運用は承認しません。終了コード0と幾何検査だけでは内容・可読性の承認になりません。

**ここで終了できる評価範囲**は、同一セッション・同一固定版スキルを復旧して制作した3枚について、完成画像の比較、指定された5工程の観測可能性、原典抽出・生成・検査の成否、監督の内容介入範囲を評価することです。このレビューでその範囲は完了しています。追加の全図探索や全イベントの重複精読は不要です。

**まだ主張できない範囲**は、MIRU講義全体の構成・整合・図版品質、本番自律運用の失敗率、読者理解や会場投影、異なる環境での再現性、旧版に対する最新版スキルの因果的な性能向上です。これらは今回の結果を不合格にする条件ではなく、別の評価を要する主張です。
